# 2.3 提示词工程

## 摘要

这一讲从"模型能力正在以极快的速度跃迁"讲起，说明为什么在模型越来越强的今天反而更需要提示词工程：模型进步不是线性的，任务正在从"会答题"转向"能独立完成复杂任务"，而上下文窗口始终是有限且昂贵的资源。课程拆解了模型的上下文窗口、滑动窗口与上下文压缩机制，把提示词按信息类型分为六类、按来源分为系统提示词与用户提示词，并给出好提示词的三条原则和一份"七格任务说明书"模板。核心内容是六个可复用的技巧：先问关键问题、先写计划再实施、设计并迭代系统提示词、注重格式分割、先零样本失败再补少样本、让模型扮演具体角色。最后以一个"个人网站"项目串联全部技巧，演示从需求澄清、MVP 方案、需求冻结、UI 规范到分步开发与验收的完整闭环，并交代了隐私、时效、高风险领域复核、提示词注入与中转站等使用边界和课后作业。

### 核心要点

- **模型能力的跃迁**：2023 年的 GPT-3.5 Turbo 面对"妹妹是一半年龄"只会套用比例（捷径学习），2026 年的 GPT-5.6 Luna 会先找不变的年龄差，给出 67 岁；数学、推理、代码、操作电脑等基准上，正确率在几个月内从个位数跃到超越人类极限。
- **长线任务能力**：模型连续工作时长大约每 7 个月翻一倍，GPT-5 能以约 50% 的概率独立完成人类专家需 2 小时 17 分钟的任务，AI 正从"答题"转向"独立执行任务"。
- **提示词工程的目标**：不是应付"门锁锁芯有几个级别"这类日常问答，而是设计能指导模型以较高完成度、较优雅的方式、较少返工去实现"一句话说不清"的复杂任务。
- **上下文窗口的由来**：每多记一个 token 就要多保存中间信息（KV Cache）、多做 attention 计算，显存与算力成本上升，所以窗口必须有限；窗口不是模型故意遗忘。
- **滑动窗口**：把对话想成一条长纸带，模型只能透过固定宽度的窗口看一段，新 token 进来就把最旧的挤出去，以此保持固定长度。
- **提示词的六类信息**：指令、外部资料、输入材料、训练约束、对话历史、上下文压缩，六者拼接成模型真正看到的提示词，改动任何一部分都可能改变输出。
- **训练阶段的约束**：DeepSeek 拒绝回答如何制作炸药、Claude 在网络安全攻防话题上拒答，都是训练方设定的边界。
- **上下文压缩**：早期是暴力截断（滑动窗口，已基本被抛弃），现在主流是摘要压缩——不等比例缩短，而是决定哪些必须保留、哪些可摘要、哪些可丢弃；系统提示词在每轮压缩中被完整保留。
- **好提示词三原则**：目标对象动作无歧义、只给当前任务所需的信息、事实格式与成功标准可验证。
- **七格任务说明书**：目标、背景、材料、动作、约束、输出格式、验收标准，只填会影响结果的部分。
- **六个关键技巧**：先问关键问题（头脑风暴）、先写计划再实施、设计并迭代系统提示词、注重格式分割、先 zero-shot 失败再补 few-shot、角色扮演要具体到领域与受众。
- **实战闭环**：个人网站案例依次走需求澄清 → MVP 方案 → 需求冻结 → UI Style Guide → 分步开发 → QA 代码审查 → UX 优化 → 项目验收，复杂任务靠分步提示词完成，而不是追求一个终极提示词。
- **使用边界**：不上传隐私、注意资料时效、高风险领域必须由专业人员复核、警惕网页邮件 PDF 中的指令注入、警惕 AI 中转站注水，对外发布前必须人工审核。
- **课后任务**：基于第一节课的项目准备卡，产出一份用于生成静态简历网页的提示词，交给任意网页 AI 生成 `.html` 文件。

### 课后任务

- 基于第一节课形成的「项目准备卡」，结合本节课学到的提示词工程技巧，产出一份用于生成**静态简历网页**的提示词。
- 把这份提示词交给任何一个网页版 AI，让它生成静态页面的 `.html` 文件。上节课说过，第二次课之后每位同学都要形成自己的静态简历网页。

## 讲稿

### 开场：这一讲要解决什么问题

**吕老师（录音）**：亲爱的同学们，欢迎来到 AI 入门第二讲——提示词工程，我是卓才教育的吕老师。在上节课"与 AI 的第一次协作"中，我们初步认识了提示词，也看到了提示词好坏会带来完全不一样的效果。这节课我们会针对提示词做进一步的展开：把想法说清楚，理解提示词工程与上下文的原理，掌握一些任务框架与实用技巧，用系统的方法去设计、迭代并验证复杂任务场景。

### 一、模型能力的跃迁

**吕老师（录音）**：首先我们补充一个背景：模型的能力正在以一种极快的速度迭代增强。先看一个例子。2023 年 3 月的 GPT-3.5 Turbo，面对这样一个问题——"当我 6 岁时，我的妹妹是我一半年龄，现在我 70 岁了，我的妹妹多大？"——它把"妹妹是我的一半年龄"错误地理解成"永远是一半"。2023 年的模型只抓住了表面模式，直接按一半的比例去算，认为这是一个永远不变的比例关系。这是比较典型的"捷径学习"：它只学到了表面关联，而没有真正建立时间关系。

**吕老师（录音）**：而在 2026 年的今天，能力最强的 GPT-5.6 Luna，测试时就能发现正确的思路：它先去找到年龄差，而不是直接去算比例。你 6 岁的时候妹妹 3 岁，所以年龄差是 3 岁，而年龄差始终不变，因此它给出正确答案 67 岁。我们能看到，2023 年的模型不会有一个真正的推理过程，而 2026 年的模型能够抓住那个保持不变的逻辑。

**吕老师（录音）**：这个例子不那么直观，接下来我们看一些更直观的数据对比，感受一下模型能力的跃迁或者迭代速度有多快。

**吕老师（录音）**：第一组是 AMC 数学竞赛。4 个月的时间里，模型从做对 2 道题到做对 11 道题，有了接近 60% 的正确率提升，同样都是高难度的数学推理。在 2024 年 5 月，GPT-4o 在 15 道题中只做对了 1.8 道，正确率 12%；而在 2024 年 9 月，4 个月过后，o1 模型在 15 道题中做对了 11 道，正确率接近 74%。在这种高难度数学推理的任务场景里，模型能力在几个月内就可能发生明显的跃迁。

**吕老师（录音）**：第二组数据是 ARC-AGI，也就是让模型像人类一样去做逻辑推理的题目，这组数据的跃迁就更夸张了。大约 14 个月的时间里，2025 年顶尖模型在 AGI 任务上的完成率还小于 5%，而到 2026 年，任务完成率已经达到 92.5%。昨天还几乎不会的新题，一年之后就被追到了 90% 以上。

**吕老师（录音）**：第三组是真实的代码场景 SWE-bench Verified。这些题不是刷题，而是人类设计出来的代码评估题，让模型去读真实的代码仓库、修改文件、通过测试。2024 年的 GPT-4o，任务完成率在 33.2% 左右；到 2025 年的 GPT-5——我们还不说今天的 GPT-5.6——这个数据已经跃迁到了 74.9%。

**吕老师（录音）**：第四组数据，是让模型去模拟人类操作电脑。在 GPT-5.2 的时候，任务完成率只有 4.4%～17.3%，而到 GPT-5.4，不到三个月的时间就达到了 75% 的水平，而人类在这项任务上的极限是 72.4%。也就是说，在这项任务的表现上，AI 已经超过了该测试当中人类的极限，它做得比人类更好。

**吕老师（录音）**：最后一组数据。我们前面看的数据都是让模型去做题，但模型不只在答题场景，它在连续完成长时间、长线任务的表现上也得到了比较大的跃升。最早期的模型只能执行秒级、分钟级别的任务；到了 GPT-4o 时代，它能够连续工作约 30 分钟；而 GPT-5 能以约 50% 的概率独立完成人类专家约需 2 个小时 17 分钟的任务，也就是一些比较深刻的问题场景。模型能够连续工作的时间，这个规律大约是每 7 个月翻一倍。

**吕老师（录音）**：所以总的来说，模型的进步不是线性的，可能几个月就有一次台阶式的跃迁。人类给模型设置的旧测试集很快就会被打穿，新的测试集也可能在短时间内被追上。AI 正在从"更会回答问题"、"更会答题"，转向"更能独立地去完成一些复杂任务"。

**吕老师（录音）**：所以说，我们今天学习提示词工程，不是为了去完成日常性的简单任务。比方说我最近和豆包交互，我问它：我们的门锁，锁芯有 A 级、B 级、C 级纯铜锁芯的区别，我不知道，我就去问豆包，让豆包告诉我这三个级别的纯铜锁芯有什么区别。这样的简单生活化问题，并不需要任何提示词技巧，你只需要清楚明确地把自己的问题用自然语言描述出来即可。

**吕老师（录音）**：真正需要提示词设计、真正需要提示词工程的地方，往往是"一句话难以描述清楚"的复杂任务。所以我们这节课的目标，或者说我们学习提示词工程的目标，更多的是去设计能够指导模型、以较高的完成度、较优雅的方式、较少的返工实现复杂任务的提示词。

**吕老师（录音）**："较高的完成度"比较好理解，那什么叫"较优雅的方式"？举个例子，如果你让人类去做一个逻辑推理，他面对所有的可能性，如果一个一个去穷举，我们说他的方式是很笨的；如果他有一定的思路，在模型的场景下，这个思路就是我们人类通过提示词工程提供给他的。结合上节课的知识，我们给他设计了一个有限的逻辑空间，他面对的可能性就比较少，因此需要的推理、需要的上下文资源就比较少，这种方式对于模型工作而言就是比较优雅的方式。

**吕老师（录音）**：什么是"较少的返工"？就是模型在完成一次任务之后，有哪些工作效果没有达到人类的预期，需要我们人类自己去做一定的修复或者优化，这就是所谓的返工，也就是我们上节课提到的一个概念——human in the loop。我们的目标是较高的完成度、较优雅的方式以及较少的返工，然后去实现的是复杂任务，而不是简单的生活化问题。

### 二、为什么模型越强，还需要提示词工程

**吕老师（录音）**：那么问题来了：模型的能力越来越强，迭代速度只会越来越快，能力只会越来越强，为什么我们还需要提示词工程？一个核心的原则是——为了去更好地利用上下文窗口，以更小的成本、更好的效果与模型交互。

**吕老师（录音）**：上节课我们简单提到过什么是上下文，也就是当前模型基于什么信息来给我们回复。它基于的不是我们简单发给它的一句指令，而是它获得的所有的这些信息，这些信息就称之为它的上下文。而上下文是一种非常宝贵的资源，因为上下文窗口是有限的。所以提示词工程的目的，就是为了更好地去利用上下文窗口。

### 三、上下文窗口是怎么工作的

**吕老师（录音）**：为什么会有上下文窗口限制，或者说上下文窗口到底是个什么东西？模型每多记住一个 token，就要为它保存更多的中间信息，并在生成后续内容时继续参考这些信息。也就是我们第一节课举的例子：它像一个文字接龙高手，每预测下一个 token，都是基于当前所有的 token 来做概率推算；推算出下一个 token 之后，它就会把新的 token 加入到已有的所有 token 的列表里，也就是我们所谓的上下文，形成一个新的上下文。上下文包含的 token 越来越多，它需要保存的信息越来越多，上下文越长，显存、计算量和训练成本都会不断增加，因此上下文不可能无限长。

**吕老师（录音）**：下面这张图设计的专业概念比较多，大家只听个响就好，它并不影响你的理解。我们只需要知道：上下文窗口不是模型故意的遗忘，而是因为 Transformer 是大语言模型的训练架构，它在处理已有的这些 token 时，需要为它们持续保存一个叫做 KV Cache 的东西，也就是我们上面提到的中间信息，并执行一个叫做 attention（自注意力）的计算。

**吕老师（录音）**：attention 怎么理解？直观的理解是，我们基于已有的上下文，就像人类一样：我前文有一个代词提到"他是小明"，下一句话我不用说"他是小明"，不用重复，我们都知道他是小明，这就是人类具有的上下文理解能力。模型一开始是没办法完成代词转化的，第一句话提到"他是小明"，下一句话它就忘了他是谁。所以 attention 就是帮助它跨越比较多的 token 或者比较多的提示词，去完成记忆联系的一个功能。

**吕老师（录音）**：随着上下文的增长，显存与计算成本就会迅速增加；同时模型训练也只能针对有限长度的上下文进行学习，因此模型就必须设置一个有限的上下文窗口。所以基本的逻辑链路是这样：更多的 token 需要更多的 KV Cache，需要存储更多的中间信息，就会有更多的 attention 计算，就会导致更高的显存算力成本，上下文不能无限增长。

**吕老师（录音）**：接下来我们看一个 `.html` 文件的动态演示。我们刚刚解释了什么是上下文，那么为什么叫"上下文窗口"？大家可以把整段对话想象成一条很长的纸带，模型一次只能透过一个有限大小的窗口看到其中一部分。看动画：当前窗口当中包含了这些词——"用户：请根据前面的所有对话总结"——我们这里设置的窗口大小是 7 个 token，这里是不是已经有 1、2、3、4、5、6、7 个 token，上下文已经满了？

**吕老师（录音）**：当它预测下一个 token 的时候会怎么做？新的 token 来了，上下文长度继续增长，但是窗口已经满了，达到上限，它就不能无限地保留所有历史。所以窗口就会向右滑动，把最旧的 token——"用户："——移出去，然后把最新的 token 挪到当前的窗口里来，再基于现在新的上下文窗口去预测下一个 token。这里就把刚刚最旧的一个 token 移出了窗口，把最新的 token 移了进来。窗口的名字就是这么来的。

**吕老师（录音）**：也就是说，模型并不是永远拥有整段历史，而是像隔着一扇窗，隔着这么一个窗口去看一条长纸带。窗户有多宽，最多就同时看到多少 token，也就是模型的上下文有多大。为什么叫"滑动窗口"？就是当窗口装满了之后，新的 token 再进入窗口，它就有一个整体向右滑动的过程：把最旧的一个 token 丢出去，把最新的一个 token 加进来，从而保持固定的上下文长度。

**吕老师（录音）**：为什么这么做？因为它的上下文窗口不是无限的，token 越多，需要保存中间信息所付出的代价就越大，所以我们需要把窗口固定下来，从而把资源的开销控制在比较可以接受的范围。一句话理解上下文窗口：它就等于模型一次能看见的最大文本范围；而滑动窗口就是这个范围随着新内容不断丢弃最旧的 token、装入最新的 token 的过程。

### 四、热身：什么样的提示词是差的

**吕老师（录音）**：接下来我们看一个热身的例子。比方说我给 AI 的提示词是这样一句话："帮我把这份材料做得更好。"这句话我们究竟要求 AI 怎么做？它有三个很明显的缺口：第一，交付对象是谁，这份材料我要交给谁？第二，"更好"指的是什么更好，我应该依据什么标准去判断这份材料是变得更好还是更坏？所以这是很差的提示词。

**吕老师（录音）**：我们在第一节课接触过提示词，也就是所谓的 prompt 这个概念。这节课我们来系统地讲一下什么是 prompt。

### 五、提示词的六类信息

**吕老师（录音）**：首先按信息类型划分，提示词大致分为六类。

**吕老师（录音）**：第一类，**指令**。我们与模型在每一次任务对话当中发给它的这些内容，比方说我提的一个问题、要求它帮我去搜索一些内容、要求它帮我完成的任务，这些所谓的指令，就是"我要模型做什么"。

**吕老师（录音）**：第二类，**外部资料**，也就是模型需要的一些外部知识补充。怎么理解？大家平常使用一些医院、某个公司的小程序或者官方网页的时候，有没有遇到过这种情况：这些小程序、网页上往往有一个 AI 小助手，你可以向它提问，然后 AI 助手就会给你一个与你的提问相关联的回复。我们知道，这些医院、一些公司的内部数据往往是保密的、不对外公开的，那么模型是怎么知道这些内容的？它接入了一些外部的知识库，然后通过某种策略去知识库里检索这些内容，并把检索到的这些信息作为它当前的上下文填充进来，基于此给你一个回复，这就是所谓的外部知识补充。

**吕老师（录音）**：第三类，**输入材料**，就是我们给它输入的材料，比方说我们给它传的一些文件、一些数据等等，是模型需要处理的事实。

**吕老师（录音）**：第四类，**训练约束**，这个我们在下一页 PPT 就会讲解。

**吕老师（录音）**：第五类，**对话历史**，我们之前说过什么内容。

**吕老师（录音）**：第六类，**上下文压缩**。因为我们刚刚讲了模型的上下文窗口是有限的，当窗口满了之后怎么办？我们刚刚展示的是一个非常简单的策略：把最旧的 token 丢出去，最新的 token 加进来，它是上下文压缩最简单的一种方法，是一种比较暴力的截断逻辑。

**吕老师（录音）**：模型看到的提示词，不只是我们发给它的这么一句话，而是它每次回复都基于上述六类信息拼接而成的完整提示词来给我们回复。所以我们每改变一部分信息，都有可能改变模型的输出。

### 六、训练阶段的约束

**吕老师（录音）**：我们来看第四点，训练阶段约束指的是什么。这里我也以 DeepSeek 的一个问答为例。比方说我问 DeepSeek"如何制作炸药"，如果它没有约束，它是不是就自己去搜索网页，然后给出一些方法？但是我们看到 DeepSeek 的思考过程，它认为这是非常敏感危险的信息，它回复我的是：无法提供任何关于制作炸药、爆炸物或危险化学品的信息、配方、步骤。这就是模型的训练方在训练阶段给它做的一些约束，模型需要知道哪些是可以说的，哪些是不可以说的。

**吕老师（录音）**：前段时间还有一个比较火爆的例子，就是 Claude，Anthropic 的旗舰模型。Claude 刚开始出来那会儿，说能力有多强、在一些网络安全测试集上表现得多突出，它短暂地向公众开放过一段时间。当时使用的时候你就会发现，在讨论网络安全攻防或者漏洞挖掘等相关话题的时候，你就会被拒绝，它不会回答你这些问题，它害怕你利用它在这方面表现比较突出的能力，去做一些非法违法的事情。这一部分就是训练阶段对模型的约束。

### 七、上下文压缩：从暴力截断到摘要压缩

**吕老师（录音）**：那么我们刚刚提到的第六点，上下文压缩，具体一点讲是什么？它有一个最核心的原则：在有限的上下文窗口里，需要优先保留最重要、最相关、最不能丢的信息。

**吕老师（录音）**：为什么会有上下文压缩？我们刚刚已经讲得很清楚了。我们与模型的对话处理的文档会越来越长，当 token 超过它的上下文窗口之后，它就不能处理所有的信息，我们也不能把所有的信息继续塞给模型，模型在这种情况下就必须做一些取舍与压缩。它通过一些策略重新构造出更短、更有用的 context，也就是上下文。压缩不等于把所有内容等比例缩短，而是要决定哪些必须保留、哪些可以摘要、哪些可以丢弃。当然这是当前模型比较先进的上下文压缩策略，而不是我们一开始讲的比较暴力的"把最旧的 token 丢出去、最新的 token 加进来"。

**吕老师（录音）**：我们来看原始的上下文有哪些内容。没经过压缩的上下文，首先包括一些提示词、最近的几轮对话、很久之前的一些历史对话；它可能调用了一些工具，返回了调用结果；然后是一些外部的文档资料，以及当前的用户问题是什么。这是一个完整的上下文组成。现在上下文窗口已经超了，它就会进行上下文压缩。

**吕老师（录音）**：上下文压缩常见的方法，第一个就是我们刚刚讲到的直接进行暴力截断的逻辑——滑动窗口，把最旧的 token 丢掉，最新的 token 加进来，像一个窗口一样不断地向前滑动。这是一些早期的上下文压缩策略，现在已经基本被抛弃了。它的问题是什么？它没有区分在已有的上下文当中哪些信息是重要的、哪些必须保留、哪些可以摘要、哪些可以丢弃。

**吕老师（录音）**：所以我们有了第二种压缩方法，叫做**摘要压缩**：把长历史对话总结成更短的摘要。模型后台可能会调用一些参数量比较小的模型，或者其他的模型，对当前已有的上下文信息做一个总结、提炼、概括，总结成更短的摘要，最后形成压缩后的提示词。上下文压缩的核心，不是尽量去保留更多的字，而是在有限的预算里让模型看到最有用的信息。

### 八、系统提示词与用户提示词

**吕老师（录音）**：提示词还有一种分类，是按照信息来源来区分，分成系统提示词和用户提示词。什么是系统提示词和用户提示词？

**吕老师（录音）**：一句话解释：系统提示词决定的是模型"怎么工作"，而用户提示词决定了这一次任务具体要模型"做什么"。系统提示词更像一份说明书，更像一个员工必须遵守的工作守则，每一次任务都要在工作守则下进行；它往往是由平台、应用或者开发者预先给模型编写的一些高级规则，用来规定模型的角色、风格、边界以及输入输出方式等等。

**吕老师（录音）**：角色、风格、边界、输入输出方式，大家比较好理解。我们希望模型在每一次对话、每一次任务当中都具备这些信息，而不是我每新开一个会话、每新执行一个任务，就要把角色、风格、边界、输入输出方式有关的提示词又复制一遍。而用户提示词更像给员工下达的一个具体任务，它只是告诉模型这一次要回答什么、要完成什么。

**吕老师（录音）**：这里有一个例子。系统提示词："你是一名面向高中生的 AI 教师，你的回答要通俗易懂。"它给模型定义了这样一个角色和风格。而当前任务的用户提示词是："什么是大模型的上下文窗口？"所以当前的提示词就不单单是这一句话，而是系统提示词和用户提示词拼接的结果，模型会基于拼接结果完成回复。所以说，系统提示词告诉 AI"你是谁、该怎么做"，用户提示词告诉 AI"我现在就当前这轮任务要你怎么做"。

**吕老师（录音）**：还有一个比较重要、比较核心的点：在我们刚刚讲的上下文压缩的概念当中，系统提示词在每轮压缩当中都会被完整保留，它不会被压缩、不会被提炼、也不会被总结，它在每一轮压缩中都会被完整地保留下来。它是对模型最底层的约束，也是最重要的信息。所以我们现在知道了，模型在每一次的上下文压缩当中，压缩的往往是用户提示词。

### 九、好提示词的三条原则与七格任务说明书

**吕老师（录音）**：那么一份好的提示词是怎么样的？有三个跨模型都有效的原则。第一个，你描述的目标、对象、动作一定不能有歧义，必须要清晰。第二个，你只给模型完成当前任务所需要的相关信息，不能扯东扯西，给它扯一堆没用的。第三个，你的事实、格式与成功标准要可验证、可检查——不能说模型给你的回复、帮你完成的任务连一个边界都没有，那你怎么知道它完成了？所以说一句话：只去写清会影响结果的变量，删掉只会增加噪声的装饰。

**吕老师（录音）**：怎么理解？我们先看一个短而明确的、比较好的提示词，再看右边一个长而空洞的提示词："你是宇宙最顶级、最有创意、最懂年轻人的超级文案大师，以震撼、完美、绝对优秀的方式写一份史诗级的活动宣传。"我给了你很多形容词，写得天花乱坠，但是关键信息很少，大部分形容词与当前任务都是无关的。

**吕老师（录音）**：我们总结了一个方法论，大家可以按照这个方法来编写提示词。第一个，**目标**：你要描述清楚为什么让模型去做这个任务，为什么这么做。第二个，**背景**：你需要给模型提供哪些背景，它的受众是谁，谁在什么场景下使用这个东西。第三个，**材料补充**：模型要完成任务、回答你的问题，需要依据哪些信息。第四个，**动作**：需要模型去做哪些动作，比方说我可以先把任务手动拆分成可复用的、比较明确的几个动作，1、2、3、4 分别是什么，让模型按照我给它动作去做。第五个，**约束**：这次回复字数限制是多少，要以什么语气回复，哪些是不能触碰的。第六个，**输出格式**：最终模型输出的结果格式长什么样。第七个，**验收标准**：什么样才算模型完成了任务，你也要说清楚。

**吕老师（录音）**：需要注意的就是，这个"七格任务说明书"不是口诀，不是考试填空，你只用去填写会影响结果的部分。比方说有些回复不需要参考任何材料、不需要依据任何信息，那第 3 点你就可以不用写。这是一个可以复制的七格提示词模板，大家可以简单看一下并截图保存，我这里就不做过多赘述了。

### 十、技巧一：先问关键问题（头脑风暴）

**吕老师（录音）**：好，接下来进入我们这一课的重点：在写提示词、或者说提示词工程当中，有哪些比较关键的技巧。

**吕老师（录音）**：第一个技巧，**先问关键问题**。我们与模型交互的过程当中往往会发现，很多任务场景我们前面一直在说要把提示词写清楚、把问题说清楚，可是这个任务场景我都不了解，我都不是学这个的，但是我要完成这方面的工作，我该怎么写提示词？你就能用上第一个技巧。

**吕老师（录音）**：先问关键问题，也就是我们常说的与模型进行一场头脑风暴。你可以这么写。普通的提示词可能是"帮我做一个社团开放日的活动方案"，而你自己也没太想清楚这个活动方案需要具体做哪些活动，你就可以通过一个 brainstorming，也就是头脑风暴的提示词告诉它：在生成方案之前，先找出不明确的信息，每次只问我一个最重要的问题，确认目标、限制和成功标准，再提出 2~3 种方案并推荐一种，我确认后再继续。

**吕老师（录音）**：这相当于：原本是你向模型提问，现在你告诉模型"这个东西我不懂，我不知道怎么做，你来向我提问，让我来做关键决策"。它的核心流程是：让模型去理解已有的上下文信息，然后让它自己主动澄清，围绕目标、限制、成功标准来向我提问。你当然可以一次不只问一个问题，可以一次给它多个问题；但一次只问一个问题，这个流程会更清楚明确。然后让它提供 2~3 种方案——这个东西我不了解，也不知道有什么方案能实现，所以模型你给我提供 2~3 种，并说明每种方案的优劣，让我基于我比较了解的任务场景限制来做出最优选择。最后告诉模型必须经过确认：我不确认，你就不执行，等我确认过后再进入执行的阶段。不管是写方案也好、写代码也好、写计划也好，都是这样。

### 十一、技巧二：先写计划再实施

**吕老师（录音）**：第一个技巧往往搭配第二个技巧——**先写计划再实施**——来使用。你和模型把这个方案、这个问题澄清清楚之后，如果你是让模型去写代码，你让它马上开始写代码，它往往效果不好；更好的做法是先让它生成一个计划，再让它去实施。在开始执行任务前先编写计划书，再按照计划分步骤执行，能够显著提升任务的可靠性与可控性。

**吕老师（录音）**：它的整个流程是：首先明确任务，明确目标、输入的格式、有哪些约束条件、什么样这个任务才算成功，把这些约束列清楚；然后让模型去编写计划任务书，既然叫计划书，就要把每一个步骤都写清楚，也就是把当前可能比较大的任务拆分成能够独立完成的多个小任务；再让模型按照任务书一步一步去执行，每一步任务都应该产出比较直观的、我们可验证、可感知的结果；最后检查、验证、总结与交付。

**吕老师（录音）**：核心的原则是：先让模型想清楚，或者说我们自己先想清楚再动手；一次只完成一个步骤，只做一件事。示例可以这么写："先帮我制定一个详细的执行计划，将任务拆分成具体的步骤，每一个步骤说明目标、方法和预期输出，评估可能的风险与应对策略，待我确认计划后再按计划逐步执行。"这就是 human in the loop 的体现。

**吕老师（录音）**：这里也有一个数据，可以展现"先写计划再实施"对模型的任务表现有比较大的提升。它能够帮助模型减少错误与幻觉，得到更高的准确率；有更好的可控性，因为步骤是清晰的，我们可以追溯是哪一步出了问题；有更高的效率，也就是我们一开始提到的以较少的返工完成任务；还有更强的可靠性。

### 十二、技巧三：设计并迭代系统提示词

**吕老师（录音）**：第三个技巧需要结合我们刚才讲的系统提示词。我们需要去合理地设计当前任务场景下的系统提示词是什么：我们在每一次与模型交互、每一次任务当中，它都需要知道的知识是什么？

**吕老师（录音）**：系统提示词往往放些什么内容？这里给大家列了 8 个点：角色与身份；目标与任务；能力范围与边界；知识依据；行为准则；安全与合规；工具使用与流程；长期记忆与偏好。系统提示词不只是一次普通提问，而是给模型先定规则——这就是我需要你遵循的这些规则，再让它执行任务。

**吕老师（录音）**：第二个问题，该如何迭代优化系统提示词？写提示词往往不是一蹴而就的，系统提示词也需要迭代优化。你不可能一上来就一次性把完成当前任务所需要的所有约束、所有硬性规则、所有最底层的这些信息都写清楚，所以你需要有这么一个迭代的过程：先搭初版，先写 1~3 条关键约束，然后让模型去测试验证，看看我的约束有没有效果；出了问题去定位问题在哪里，并针对这个问题做一个精准的优化，然后再进行验证，有这么一个迭代的过程。系统提示词不是一遍写完的，而是通过测试不断打磨出来的，写任何提示词都是这样。

**吕老师（录音）**：写系统提示词时需要注意的事项：首先，你要避免你写的系统提示词相互冲突；其次，不要因为系统提示词是对模型最底层的约束、保存的只是最重要的信息，就对它做过多的限制，限制太多就会影响模型的灵活性与回答质量；然后，以小步快跑的方式，每次只做小步的修改，反复迭代优化，最终达到稳定的效果。

### 十三、技巧四：注重格式分割

**吕老师（录音）**：第四个技巧是**注重格式分割**。我们在第一节课也提到了 Markdown 语法。当我们的提示词比较复杂、结构比较复杂的时候，就需要通过格式分隔的方式去减少可能存在的歧义。

**吕老师（录音）**：比方说 Markdown 语法。这是一个比较著名的工作流，一个头脑风暴的提示词，它也运用了格式分割技巧：三个短横线就是分割线，一级标题、二级标题，以及一些有序列表和加粗等等。用 Markdown 语法或者说一些显式的标签语句来分割提示词，能够让人看得更清楚——你在这种情况下能看得更清楚，模型也能看得更清楚，它就能更容易理解你的意图。你也可以通过加粗的记号去告诉模型，我认为这些是需要重点关注的信息。

**吕老师（录音）**：这是我们第一课讲过的图，这里再带大家回顾一遍：短横线是无序列表；数字加冒号加空格是有序列表；星号是加粗；一个反引号是针对单个字词的行内代码块，三个反引号就是一整片的代码块；一个井号是一级标题，两个井号是二级标题，三个井号是三级标题。

### 十四、技巧五：先零样本，失败再补少样本

**吕老师（录音）**：第五个技巧，**先零样本，失败了再补少样本**。这是什么意思？我们看一个任务场景：我需要模型来判断下面这条用户留言属于投诉、咨询还是表扬，而且它只说出类别名称，方便我进行数据统计。

**吕老师（录音）**：用户的留言是"为什么我的订单三天了还没有发货"。我们看到模型的回复是："这属于投诉类问题，因为用户对订单迟迟没有发货表达了不满。"虽然分类是对的，但是它没有按照我们的要求只输出类别名称。我们来诊断一下，失败的原因是什么？问题不在于它不会分类，而是输出的格式不稳定，它多说了额外的内容。

**吕老师（录音）**：这个时候你不用把提示词说得很复杂，而是针对它失败的这一个点，只去补充几个案例——它在这个点上表现得不好，我就补充一下。像这里，few-shot 的意思就是我补充了几个示例：示例一，用户留言"请问会员什么时候到期"，输出"咨询"；然后输出"表扬"；然后输出"投诉"。就是针对性地补充几个正确回复的案例，也就是所谓的 few-shot。

**吕老师（录音）**：你不能一上来就 few-shot，而是先 zero-shot，不把正确的示例加上：成功，皆大欢喜；失败，再按照具体的失败场景、失败原因去补充 few-shot。few-shot 不只是补知识，更重要的是用示例来定义标签、定义格式、定义回答方式。整个流程就是：先 zero-shot，诊断失败再 few-shot。

### 十五、技巧六：角色扮演

**吕老师（录音）**：技巧六，大家可能见得比较多：让模型去扮演某个角色。扮演专家这里也有好坏之分。我告诉模型"你是世界顶级专家，请给出最完美的答案"，这其实也是一个空而大的提示词，它没有受众、材料、任务与成功标准，什么都没有说清楚，这样的专家扮演是很失败的。

**吕老师（录音）**：如果告诉它"你是一名面向高中毕业生的课程助教，术语首次出现时用一句生活化类比解释，不虚构来源"，这是不是一个比较有效的角色？比较有效的专家扮演，会让模型检索的信息、检索的内容收束在你给它限制的角色范围内，领域、受众、可观察的行为都说得很清楚。

### 十六、实战案例：个人网站开发

**吕老师（录音）**：接下来我们来进行一个实战的提示词编写案例：实现一个个人网站，要求包含如下功能——上传单词与背单词、简历维护与可视化、短期的任务规划拆解和提醒、课表录入和提醒、预习复习。

**吕老师（录音）**：虽然我们的提示词只有这几句话，你觉得这是一个很简单的任务吗？光从这几个功能而言，我认为这是一个比较复杂的工程场景。所以你不能通过提示词的长短去判断任务的复杂度。往往看起来越简单的任务，包含了越多的不确定性逻辑：模型面临的逻辑空间越大，它需要推理的可能性就越多，任务回答质量就会显得降低。这里我们就结合一个网页，讲讲我对这个个人网站 prompt 的迭代是怎么做的，以这个为例给大家讲解提示词怎么迭代。

#### 第一版：先别写长，先问清楚

**吕老师（录音）**：首先，刚开始我们可能只是一个很普通的 prompt："帮我实现个人网站，有如下几个功能，帮我把网站做出来。"这个提示词写得好不好？换一个角度问：你是开发者，你面对这样的需求——甲方告诉你需要你这么做——你难道可以直接写代码吗？这里存在大量未知信息。所以模型面对需求，不管它是模型也好、人类也好，面对的就是一个非常大的逻辑空间，可能性是没办法穷举的。网站是谁使用？电脑优先还是手机优先？数据应该存在哪里？上传支持什么文件？简历可视化怎么把简历展示在网页上？到底用什么技术？

**吕老师（录音）**：第一版，因为我们这个产品也是一个迭代的过程，不可能你上来就端出一个非常完美的产品，所以说第一版要做哪些内容，我们都不知道，不确定性太多了。这个时候最重要的事情，不是我要把提示词写得更长，而应该问问自己、问问模型：为了完成任务，还有哪些真正重要的信息没有确定？这时我们就用到了第一个技巧。

**吕老师（录音）**：头脑风暴。我们不知道这个代码怎么写，你不了解、你不是学这个的，我们可以一上来就问 AI，告诉它"我只有一个比较模糊的产品想法"，这里就运用了一个角色扮演："你像一个产品经理一样，先帮助我澄清那些真正会影响产品设计与技术实现的问题，最多提出 8 个关键问题。"这里是不是就用到了头脑风暴？所以它就会开始问你一些问题。这里只是我的一个示例回复。

**吕老师（录音）**：这里有一个需要注意的点：你要告诉模型，不要来逼我去决定每一个细节。我们这里提到的是"帮助我澄清那些真正会影响产品设计或者技术实现的问题"，而不是任何细枝末节的问题都需要来问我——影响产品整体方向的你就问，只是普通的实现细节，你使用合理的默认值就好。

#### 第二版：MVP 方案与需求冻结

**吕老师（录音）**：在需求方向已经基本明确过后，我们就会用到另外两个技巧：扮演专家，我们刚刚也用到了；以及先规划再实施的技巧。我们需要告诉它：你不要一上来就写代码，而是需要先做规划。"基于刚才已经确认的需求，现在请你同时以产品经理和全栈技术负责人两个视角来设计产品，暂时不要写代码，输出一份 MVP 的产品方案。"MVP 指的是什么？就是一个最小化的产品，它实现了我们产品基础的一些功能，它的一些其他功能拓展、一些优化，我们放到后边来做，以一个小步快跑的方式来实现产品。然后我需要产品方案里包含哪些内容，你就告诉它，最后给出推荐的开发顺序。

**吕老师（录音）**：扮演专家也是我们提到的：你不能给它一个大而空的专家——"你是世界第一程序员"是没有明确作用的描述，而这个阶段我们需要的是决策，产品决策与技术决策。产品决策对应的身份就是产品经理，技术决策对应的就是技术负责人，也就是所谓的全栈技术专家。在不同的阶段，角色甚至可以不同。你不能让一个完美的人来帮你实现所有的任务，你应该根据任务场景去设置、去考虑你的专家是谁：现在社会上这部分任务是由谁完成的，你就把谁的身份丢给 AI，让它来扮演角色。

**吕老师（录音）**：下一步，让人来做一次**需求冻结**，这就是 human in the loop。模型给出这个方案之后，你不能跟它说"很好，现在开始写代码了"，你需要自己去看这个方案，从功能的角度去确认你认为哪些是需要的、哪些是不需要的。因为模型是很擅长思维发散的，最开始你设计方案的时候，你也并没有把一些约束或者条件说清楚，所以它面临的逻辑空间是很大的。因此你要自己去确认一遍：哪些要做，哪些不做。然后基于此生成一个真正的实施文档，告诉它这份产品实施文档后续将作为开发过程当中的需求基准。

**吕老师（录音）**：我们就对它做了一个需求冻结，告诉它哪些该做、哪些不做，这就避免了 AI 在后边顺手帮你加了一些功能，而这些功能大部分我们都是不需要的。功能一多，又是无用的功能，又会占用 AI 的上下文资源，然后导致整体的回复质量下降。

**吕老师（录音）**：为什么这个时候开始使用结构化分割，也就是 Markdown 语法、标签语句？这就是我们刚提到的一些标签语句。因为我们现在面临的是已经出现了很多不同性质的信息，为了避免歧义，我们就要主动地、手动地给它划清这些边界，也就是我们刚讲的技巧——格式分隔。

#### 第三版：先定 UI 基调，再开发

**吕老师（录音）**：在开发之前，我们就先确定整个产品的 UI 基调是什么，也就是现在大家看到的这个页面它长什么样。所谓的 UI，它的色彩风格、页面布局等等都是 UI 的范畴。我们不可能让模型自己根据它的审美来——当前 AI 在审美这一块、在设计这一块其实表现得比较差。所以我们不能让它自己去完成这个事情，而是我们自己需要有这么一个过程。

**吕老师（录音）**：我来设计我想象中的产品是什么样：它有哪些色彩，它的页面布局等等，我自己想清楚；然后把这个基调交给 AI，让它基于此去完成整个产品的开发。

**吕老师（录音）**：这个过程是怎么样的？如果我们不限制的话，它可能就会出现一个问题：最后这四个模块——我们不是有四个功能模块吗——会不会像分别由四个人设计出来的四个网站？AI 实现的网站会非常丑，整个组起来就完全不像一个产品。所以我们需要先给 AI 设定一个统一的 UI Style Guide，告诉它整个产品需要共同使用的视觉语言是什么。

**吕老师（录音）**：大致的工作流是：先找 UI 参考，而不是凭空写提示词，因为现在已经有很多页面风格的集成网站。这里给大家推荐了好几个，比如 Figma 等等，后面文档会分享给大家，这些网站有不同的侧重点，大家下来可以自己探索。同时，也不要一找到一个页面就叫 AI 去照着做，往往更合理的方式是你找到 2~4 个风格相近、你比较喜欢的参考，让 AI 去提炼它们的共同特征，然后形成一套统一的设计语言。

**吕老师（录音）**：基于这份提示词，我们不推荐你说"复制这个网站"，而是找到多个参考、分析多个参考、找到共同规律，转化成我们自己的设计语言——是去参考，而不是机械地复制。这个地方，我们就基于这样一个指导性的提示词，让它继续去生成：有了指导，你怎么应该把这些指导落到你的开发当中？就让它去实现一个真正的设计文档，然后来决定统一的视觉风格，把感觉变成一种 AI 可执行的规则，沉淀为项目的长期上下文。

**吕老师（录音）**：下一个技巧，下一步，也就是我们之前提到的系统提示词，也就是长期写作规则——模型在每一次任务当中都会带上的这些内容。我们就要告诉它：实施文档需要它做些什么内容，这个 UI Style Guide 具体的页面长什么样，接下来我希望你怎么做、怎么和我们协作。这里就限定了它的一个任务需求、它的身份、它有哪些约束，这都给他说清楚。

**吕老师（录音）**：系统提示词我们需要注意的就是：你不能把系统提示词写太长，应该保存对它最底层的一些约束、最重要的信息、长期稳定变化很少的写作规则。

#### 第四版：分步执行与验收

**吕老师（录音）**：有了这些之后，我们前期的准备已经好了，现在我们就让 AI 基于这些所有的上下文信息，让它先去编写实施计划，让它自己想每一步应该完成什么：第一步做什么，第二步做什么。把计划书列出来之后，再让它按照一定的规则或者一定的技巧去执行计划书，一步一步地完成。接下来就是按照计划书一步一步完成页面的过程。这里我们看到，每一步都有对应的提示词。这里还需要注意的技巧，就是我们提到的 zero-shot，诊断失败了之后再补对应的 few-shot。也给大家文档，后续会分享给大家，大家可以下来看一下。

**吕老师（录音）**：最后，基本功能都已经完成了之后，这个页面当然肯定还有可以优化的方向。这个时候你不要告诉它"再帮我优化一下"——往哪个方向优化？是修 bug 吗？重构代码吗？优化当前的页面风格，还是加一些功能？你需要给它说清楚。这个时候你就可以再运用一下扮演专家的技巧：它就变成了 QA 工程师、一个 code review，也就是代码的审视者，然后按照一定的规则去重点检查哪些方面，并把它找到的这些问题划分优先级——不是每个问题都需要立刻修，划分一个优先级，当前解决优先级比较靠前的任务，并限制它、告诉它不能增加任何新业务。

**吕老师（录音）**：如果说这个页面功能已经稳定过后，我再对它做页面风格、UX，也就是与人类的交互上的优化。大家有一个没注意的点：现在比较像样的、大厂做出来的软件，比方说抖音也好，QQ、微信也好，这些软件大家用起来非常舒服，没有任何的不适感，因为这个页面的 UX 做得非常好，它考虑了很多和真实人类交互时的设计，如何提升人类真实交互的体验，它考虑了很多。我们需要等整个页面的功能稳定了之后，才来对 UI 和 UX 进行优化。

**吕老师（录音）**：所以最终，我们再按照一定的规则让 AI 去检查，或者让它自己去验收一下：让它自己去看有哪些没完成、哪些已经完成了，我们后续的优化方向有什么等等，最后再让它做一个整体的项目验收。整个项目就在我们的提示词工程下形成了一个真正的闭环。

**吕老师（录音）**：这就是提示词工程的示例。所以我们能看到，复杂的任务不是需要我们去追求一个终极的提示词，让它一次性把整个复杂任务做完；我们是分步骤的，每一次给它一部分提示词，并通过一定的设计和提示词工程，让它慢慢地把任务执行到我们想要的预期效果。

### 十七、使用 AI 的几个边界

**吕老师（录音）**：接下来，我们需要强调你在使用 AI 时的几个边界。

**吕老师（录音）**：第一，不能把你的隐私上传给 AI。

**吕老师（录音）**：第二，要注重 AI 回复你的参考资料、参考信息的时效性是如何的。

**吕老师（录音）**：第三，在一些高风险的领域，比如说医疗、法律、财务等等，万一 AI 给你的信息是错误的，你按照它去做，这个责任不会是 AI 的，而是你的。你需要去查权威来源，并由专业人员进行复核。

**吕老师（录音）**：第四，一些网页、邮件、PDF 当中的指令，默认是按数据处理的，它对于 AI 而言是一种不可信的输入，所以你在使用的过程当中要警惕注入风险。

**吕老师（录音）**：第五，现在大家不知道有没有接触过，我们国内有一个比较火的生意，叫做 AI 中转站。因为有一些人没有办法去获取国际上一些比较顶尖的模型能力，就只能通过中转站的方式。但是中转站对你而言就是一个完全不知道的黑盒子，你根本不知道里边它是怎么运行的。在这种情况下，你就很有可能遇到一些无良的商家，他很有可能给你注水：你一个问题发出去，他收你的是国际上顶尖模型的定价，但是他把请求转发给了国内一些免费的模型，或者一些比较差劲的模型，他就赚差价。其次，模型的回复是到他这边，你给他的内容也是到他这边，你并不知道他在中间中转的过程加了什么不干净的东西，你不知道。所以你要警惕风险。

**吕老师（录音）**：如果你让 AI 完成一些任务，并且要发布需求、向公众公开，你是需要为产品负责的。所以你在发布之前一定要进行人工审核；模型自我检测我们刚也提到了，最后还要去进行测试、进行验收——模型自检不能替代我们外部的人工验证。
